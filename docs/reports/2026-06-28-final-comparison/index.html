1. 결론

현재 기본값은 유지한다. zemory-sama의 fastest stable path는 gpt-realtime-2 audio-in/audio-out, reasoning.effort=low, server_vad threshold 0.5, silence 200 ms, 20 ms input chunk, 10 ms speaker callback, sounddevice low-latency I/O다.

200 ms보다 짧은 VAD silence window는 부분적으로 빠른 값이 나오지만 early cutoff가 발생했다. 193 ms와 195 ms는 n8 sweep에서 안정적이었으나 representative tail이 200 ms보다 나빠 기본값으로 채택하지 않았다.

무작위 severe delay는 raw max로 보존하되 headline max로 쓰지 않는다. 보고서는 p50, representative max, raw max, outlier count를 함께 보여준다. 이 정책은 “나쁜 지표를 숨기는 것”이 아니라 네트워크/API stall과 일반 latency envelope을 분리하는 것이다.

외부 VTuber/voice repo는 공통 fixture가 없어 latency 숫자를 부여하지 않았다. 대신 setup 가능성, 최신성, 아키텍처 패턴, zemory-sama에 반영할 수 있는 source-level lever를 비교했다.

6. 남은 병목과 다음 실험

아직 “더 이상 최적화 불가”는 증명되지 않았다. 현재 결과는 fast path의 중요한 병목을 제거했고 input chunk 및 session token cap 후보도 기각했음을 보여주지만, endpoint anticipation과 실제 device callback live rerun은 아직 남아 있다.

  1. 실제 live rerun: 10 ms playback callback과 sounddevice low-latency I/O는 API first-audio fixture에 반영되지 않는다. 실제 device callback 기준 로그로 수동 세션을 다시 측정해야 한다.
  2. Input chunk sweep: 완료. 10 ms input chunk는 n8에서 p50과 representative max가 모두 나빠져 기본값으로 채택하지 않았다.
  3. Session token cap: 완료. 현재 Realtime GA session update가 session.max_response_output_tokens를 거부하므로 자동 server VAD 응답 경로에서는 적용하지 않는다.
  4. Speculative endpoint anticipation: 최신 turn-taking 연구는 endpoint anticipation과 speculative response가 평균 latency를 줄일 수 있음을 시사한다. 다만 correctness와 interruption UX tradeoff가 커서 research profile로 분리해야 한다.
  5. WebRTC/AEC path: barge-in을 기본값으로 켜려면 laptop speaker echo 문제를 해결해야 한다. browser/WebRTC 또는 hardware AEC 경로가 필요하다.
